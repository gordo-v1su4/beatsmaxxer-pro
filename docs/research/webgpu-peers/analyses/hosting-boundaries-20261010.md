## What the peers actually do

| Boundary | MasterSelects | FreeCut |
|---|---|---|
| Frontend host | Cloudflare Pages serving a Vite `dist` build | Vercel serving a Vite/Vite Plus `dist` build |
| Editing/rendering/export | Browser WebGPU and browser WebCodecs | Browser rendering with an export Worker and main-thread fallback |
| Project persistence | Local File System Access or OPFS; storage Worker and local IndexedDB indexes | User-selected workspace folder containing project files; IndexedDB handle registry |
| Hosted application services | Pages Functions, D1/KV, auth, billing, analytics, hosted AI/provider relays | No web server-function deployment found in the inspected static configuration |
| Optional additional computation | Browser SAM2; separate native helper and hosted private AI kernel/provider services | Browser ONNX/WebGPU RIFE; separate Node/headless-Chrome render service available |

Sources and limits for each row follow below. “No server-function deployment found” describes this checkout and configuration, not a guarantee about every external deployment or future version.

## MasterSelects: browser editor plus separate hosted services

**Hosting is explicitly Cloudflare Pages, not Vercel.** `wrangler.toml` names `dist` as the Pages output directory and declares D1, KV, and an AI generation rate-limiter Durable Object. Its build runs TypeScript, Vite, and the documentation build. The Vite configuration specifies editor/about HTML entries and ES-module Workers. [Pages configuration](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/wrangler.toml#L1-L20), [production bindings](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/wrangler.toml#L46-L69), [build commands](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/package.json#L25-L31), [Vite entries and Workers](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/vite.config.ts#L439-L450).

**The editor's GPU and video encoder are browser APIs.** `WebGPUContext` requests an adapter through `navigator.gpu`; `VideoEncoderWrapper` creates a `VideoEncoder` and forwards its encoded chunks into the muxer. Changing the frontend host does not move those operations to the hosting provider. [GPU acquisition](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/engine/core/WebGPUContext.ts#L147-L156), [browser encoder](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/engine/export/VideoEncoderWrapper.ts#L158-L173).

**Saving projects also has local storage paths.** The project-root code opens OPFS or a user-picked directory with read/write permission. The repository storage client starts a module Worker; a metadata index uses IndexedDB. These are different from the D1 account/usage database. [Storage root selection](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/services/project/core/projectRootAccess.ts#L103-L129), [storage Worker](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/services/project/repository/persistence/StorageWorkerClient.ts#L6-L20), [local metadata index](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/services/project/repository/index/IndexedDBMetadataIndex.ts#L20-L30).

**Its server routes are substantial, but their existence does not imply server-rendered video.** Auth issues session cookies; checkout creates a Stripe session; analytics writes events to D1; hosted generation coordinates providers. The kernel route forwards a request upstream and returns the upstream body. Thus there are at least three distinct boundaries: browser editing, Cloudflare application APIs, and external AI services. [Session creation](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/functions/api/auth/callback.ts#L158-L190), [Stripe checkout](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/functions/api/billing/checkout.ts#L282-L306), [analytics persistence](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/functions/api/analytics/events.ts#L140-L161), [hosted generation](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/functions/api/ai/video.ts#L360-L415), [kernel forwarding](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/functions/api/kernel/%5B%5Bpath%5D%5D.ts#L163-L183).

**AI is not uniformly hosted.** The SAM2 Worker creates ONNX Runtime sessions using browser WebGPU with WASM fallback, and its smaller decoder uses WASM. MatAnyone has a separate native-helper client boundary. The README describes an optional native CUDA/OptiX preview while saying video export still uses WebGPU; that is a documentation claim, not a live verification performed here. [Browser SAM2 sessions](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/services/sam2/sam2Worker.ts#L63-L91), [MatAnyone helper commands](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/src/services/nativeHelper/nativeHelperMatAnyoneCommands.ts#L24-L45), [native-preview documentation](https://github.com/Sportinger/MasterSelects/blob/db912a05028eada21d37ec76d5317a36de865af2/README.md#L129-L129).

## FreeCut: static frontend, local processing, optional render service

**Its Vercel setup is static.** `vercel.json` specifies framework `vite`, output `dist`, and a catch-all rewrite to `index.html`. It also sets asset caching and cross-origin isolation headers. The current build command uses Vite Plus (`vp build`), although local agent documentation still describes older npm/Vite commands. No TanStack Start dependency or deployed Vercel function entry is present in the inspected setup. [Static Vercel configuration](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/vercel.json#L1-L49), [actual package scripts](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/package.json#L6-L35).

**Export starts a browser Worker and can fall back to the browser main thread.** This is client computation even when the JavaScript was downloaded from Vercel. The Vite build includes a second, UI-less headless harness entry for the optional CLI/service. [Export ownership](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/features/export/utils/render-pipeline.ts#L235-L283), [headless build entry](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/vite.config.ts#L123-L138).

**Persistent project files belong to a granted local workspace.** The app blocks its router behind `WorkspaceGate`; creating a project writes JSON atomically under the workspace root. IndexedDB is used for non-serializable directory/file handles. [Workspace gate](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/app.tsx#L74-L82), [project write](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/infrastructure/storage/workspace-fs/projects.ts#L231-L245), [handle registry](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/infrastructure/storage/handles-db.ts#L1-L24).

**FreeCut already performs real RIFE interpolation in the browser.** It downloads ONNX model bytes, selects browser WebGPU when available, and falls back to WASM if GPU session creation fails. A module Worker decodes source frames, synthesizes frames, encodes a higher-rate MP4, and writes OPFS scratch output for import. This is more than changing playback speed or repeating existing frames. [Inference implementation](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/infrastructure/interpolation/rife-interpolator.ts#L109-L169), [Worker creation](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/features/media-library/services/frame-interpolation-service.ts#L75-L110), [decode/inference/encode boundary](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/features/media-library/workers/frame-interpolation-worker.ts#L1-L15).

Its contract is **a source-FPS multiplier**, not a universal exact 96 FPS target. It caps inference/render pixels at `1920 * 1088`; comments describe memory and throughput tradeoffs, but their measurements were not reproduced here. A 24 FPS source at 4× yields nominal 96 FPS; the same multiplier on another source does not. Therefore it is architectural evidence for local inference, not proof that Beatsmaxxer should replace its server pipeline or can guarantee 96 FPS in every browser. Its WASM fallback also conflicts with Beatsmaxxer's existing GPU-only interpolation requirement; copying that fallback would change the product contract. [Output rate calculation](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/features/media-library/workers/frame-interpolation-worker.ts#L146-L165), [resolution ceiling](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/infrastructure/interpolation/rife-interpolator.ts#L45-L56), [WASM fallback](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/infrastructure/interpolation/rife-interpolator.ts#L158-L166).

**There is also an optional self-hosted render service.** `headless/serve.mjs` launches one warm Chrome instance, probes its WebGPU adapter, and serves render/edit/frame APIs from Node. Processing then happens on the machine running that Chrome process. It is separate from the static Vercel configuration. The service defaults to loopback because it has no authentication; its Docker recipe deliberately binds to `0.0.0.0` and documents real NVIDIA GPU support versus software Vulkan. This code proves an available self-hosting architecture, not that this user's instance is deployed. [Warm browser service](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/headless/serve.mjs#L177-L207), [API/network boundary](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/headless/serve.mjs#L702-L710), [Docker GPU and bind configuration](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/headless/Dockerfile#L40-L57).

## What TanStack changes

FreeCut uses **TanStack Router** to create its browser route tree and render a `RouterProvider`. Router handles navigation, route loading, and related application state. It does not choose where WebGPU executes. [FreeCut router setup](https://github.com/gordo-v1su4/freecut/blob/4d62e8082c5eb387a96275bcbd323d28f6e41a62/src/app.tsx#L1-L14), [official Router overview](https://tanstack.com/router/latest/docs/overview).

**TanStack Start** is a different, full-stack framework built on Router, adding server rendering, server/API routes, server functions, and client/server builds. It can target different hosts, but adopting it does not itself remove server functions or move video processing. [Official Start overview](https://tanstack.com/start/latest/docs/framework/react/overview).

## Implications for Beatsmaxxer

These are architectural inferences from the peer evidence, pending the separate Beatsmaxxer endpoint/deployment audit:

1. **Frontend hosting and video computation can be selected independently.** FreeCut is direct evidence that Vercel can serve only static assets while browser Workers do media processing. MasterSelects is evidence that hosted account/AI APIs can coexist with local editing.
2. **Keep each heavy task's ownership explicit.** Browser GPU work stays with the browser. A server GPU interpolation job belongs to an owned GPU worker/service. A static host or small authenticated API can coordinate that job without performing inference itself.
3. **A homelab static host is a deployment choice, not a framework rewrite.** The portable asset boundary illustrated by both peers can be reproduced using HTTPS, correct isolation headers, asset MIME/caching, and SPA routing. Moving MasterSelects' entire backend would additionally require replacements for its Cloudflare-specific bindings; copying `dist` would not preserve those APIs.
4. **Do not confuse baked output FPS with real-time browser throughput.** FreeCut's local inference demonstrates capability, not a cross-device performance guarantee. Beatsmaxxer's 96 FPS preparation requirement (24 FPS × 4, with a minimum of 96 FPS for other supported inputs) needs its own source-rate and output verification.
5. **The reported “12 functions” remains a Beatsmaxxer deployment question.** Neither peer's source identifies that dashboard count, quota, deployed bundling, request volume, or error. It must be explained from Beatsmaxxer's actual built/deployed routes and current provider evidence before selecting a migration.

No production host was changed. No live-cost, quota, account, or deployment claim was inferred from a README.

## Hosting choices to evaluate, without implementing a migration

The accompanying Beatsmaxxer audit reports that the app already uses `adapter-static` with SSR disabled. It identified five intentional Vercel entries: access gate, analysis/storage-upload proxy, Studio submit, Studio polling, and media jobs/upload/retry proxy. Nine helper TypeScript files were also being counted; moving the three shared-library helpers from `api/lib` to `api/_lib` brought a preview deployment below the cap. These are findings supplied by the parent audit, not separately verified in these peer checkouts. A successful preview resolves packaging pressure; it does not establish the right long-term service boundaries.

| Choice | Frontend | API, uploads, analysis and GPU jobs | Consequence |
|---|---|---|---|
| Static-only Vercel plus owned services | Keep the existing static Svelte app on Vercel | Browser calls an authenticated owned API/storage service; GPU jobs execute on the existing GPU server | Preserves Vercel frontend deployment while taking intentional backend work off Vercel |
| Full self-hosting | Serve the same static Svelte build from the homelab behind HTTPS | Owned API/storage and GPU worker remain separate services behind the reverse proxy | Removes Vercel from this app's serving path and makes the homelab responsible for availability and deployment |

Both choices retain the existing Svelte frontend. FreeCut's TanStack Router is not a reason to rewrite Beatsmaxxer to React or TanStack Start.

An external rewrite that still forwards requests through Vercel can move backend execution, but media bytes still traverse that forwarding path. It must not be presented as removing Vercel's media-transfer bandwidth. Direct API/object-storage requests require deliberate authentication, CORS, and cookie handling. The unauthenticated FreeCut headless service is useful architecture evidence but must not be exposed unchanged as a public production API.

## Pindeck: why its Vercel boundary is different

Additional read-only comparison at local HEAD [`57544eac400bf5e8c8c4f69ef248b31a2897e4e8`](https://github.com/gordo-v1su4/pindeck/commit/57544eac400bf5e8c8c4f69ef248b31a2897e4e8), checkout `C:/Users/Gordo/Documents/Github/pindeck`. No pull was requested or performed. Existing untracked `opencode.json` was preserved. These are source/configuration findings; no live deployment, dashboard quota, media request, or production-health check was performed.

- **Vercel serves a static React/Vite frontend.** Its configuration builds `dist` with Bun, declares a Vite frontend service, and rewrites browser routes to `index.html`. There is no root Vercel `api/` function tree in the inspected checkout. The `experimentalServices.frontend` declaration is a frontend entry, not evidence that Convex functions run as Vercel functions. [Vercel configuration](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/vercel.json#L1-L18), [Vite output](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/vite.config.ts#L66-L70).
- **The browser connects to Convex directly.** `main.tsx` creates a `ConvexReactClient` and mounts Convex/auth providers. The topology documentation identifies this as a self-hosted Convex backend, with separate self-hosted Trigger workers and RustFS/S3 media gateway. Thus Pindeck has server functions, but they belong to Convex rather than a Vercel `api/` deployment. [Browser Convex connection](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/src/main.tsx#L30-L52), [documented production roles](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/docs/architecture/platform-topology.md#L5-L16).
- **Durable media processing is server work, outside Vercel.** Convex's image-persistence path requires a media gateway and sends the image to its authenticated `/process-image` endpoint. Trigger upload/ingest/repair tasks call authenticated Convex orchestration HTTP actions. The inspected code proves where these requests originate; the media-gateway implementation itself is not in this inspection. Pindeck is not evidence that all processing must happen in the browser. [Image persistence](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/convex/mediaStorage.ts#L586-L620), [gateway processing request](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/convex/mediaStorage.ts#L410-L442), [Trigger tasks](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/src/trigger/mediaPipeline.ts#L16-L38), [authenticated orchestration](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/src/trigger/mediaPipeline.ts#L114-L129).
- **Build-time deployment is distinct from request-time hosting.** During a configured Vercel build, `scripts/build.ts` runs `convex deploy --cmd ...`; production builds fail without Convex deployment configuration. That deploys a separate Convex backend while producing frontend assets. The topology document says pushing `main` deploys the frontend through its Vercel project; the only checked-in GitHub workflow found is code review, so that frontend integration is documented rather than independently confirmed here. Trigger's deployment script refuses to run outside the VM100 Linux context. [Build/deploy logic](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/scripts/build.ts#L10-L46), [deployment sequence](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/docs/architecture/platform-topology.md#L46-L50), [Trigger deployment guard](https://github.com/gordo-v1su4/pindeck/blob/57544eac400bf5e8c8c4f69ef248b31a2897e4e8/scripts/deploy-trigger-vm100.sh#L1-L7).

**Inference:** Pindeck avoids this particular Vercel function-packaging pressure because its backend, background jobs, and durable media-processing boundary are outside the static frontend deployment. That does not prove its Vercel account has no other limits or that every production path is healthy. It illustrates the separation Beatsmaxxer needs regardless of frontend host.

The user has now selected full self-hosting for Beatsmaxxer, following the Review Room approach. The earlier options table records the evaluated alternatives; it is not a pending hosting-choice question. This research does not implement or verify that migration.
