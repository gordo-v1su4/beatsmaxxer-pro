# WebGPU playback follow-up: lookahead, frame lifetime and optimization risks

Checked: 2026-10-22. Research only; no renderer changes, installs or benchmarks performed for this note. Read alongside [the October 21 survey](./WEBGPU-UPDATE-2026-10-21.md) and [local optimization results](./WEBGPU-OPTIMIZATION-RESULTS-2026-10-21.md). Those local measurements and their limits remain the evidence for this application's performance.

## Findings

No newly shipped WebGPU capability since October 21 was identified in this bounded investigation. The latest Chrome WebGPU article located is still the October 7 Chrome 155–156 announcement. A recently published specification is not itself a browser release. The useful follow-up is established media-pipeline practice: prepare upcoming cut frames early, limit retained resources, and distinguish a reusable owned texture from an expiring external-video import. [Chrome blog index](https://developer.chrome.com/blog), [latest WebGPU article](https://developer.chrome.com/blog/new-in-webgpu-155-156).

Neither immediates nor shared texture bindings guarantees smoother playback. They target parameter submission and shader/pipeline duplication. They cannot make an undecoded target frame available at a cut. Keep the independently switchable QA paths and the complete-catalog fallback recorded in the local results note; evaluate latency and visual correctness separately from queue-write/pipeline counts.

## Current implementation checked before proposing more work

`VideoTextureCache.ts:4-24,47-91` already observes frame callbacks plus seek/load events, compares `uploadedRevision`, reuses same-frame views, and preserves a matching cached frame while seeking. Frame-callback upload deduplication is therefore **already implemented**, not a proposed missing feature. The Three.js comparison below supports preserving and validating this behavior.

`AppLoop.ts:341-358` resolves the current arrangement section and applies `applyTakeSection`/`enterSection` only after that section becomes current. The adjacent TimeSampler path already has resident frame-bank ownership (`PerformTimeSamplerFrames.ts:5-93`), and the parent investigation identifies future-scene preparation in TimeSampler/Timing. Do not duplicate those caches or claim that all sources load only at the boundary. The narrower question is whether ordinary HTML-video arrangement transitions can stage their **target decoder/frame** before the boundary while keeping the musical section switch at the boundary.

## External video imports are not a persistent frame bank

The GPUWeb specification defines an external texture as an immutable snapshot. An `HTMLVideoElement` import expires automatically in a task after import; a `VideoFrame` import expires when its source frame closes. Call `importExternalTexture()` again after expiry. A browser may return the same un-expired object again; object identity can permit bind-group reuse after a fresh import, but applications cannot assume reuse. Retained frames/imports can hold decoder resources and stall decoding. [GPUWeb external-texture lifetime](https://gpuweb.github.io/gpuweb/#external-textures).

Implementation implication: frame-revision deduplication may skip an unnecessary **copy to an owned texture**, but must not blindly skip re-importing live HTML video across tasks. Import, bind and submit without an intervening asynchronous boundary that allows expiration. A resident cut-cover frame should remain an owned texture or an explicitly owned live `VideoFrame`, with a clear lifetime and memory budget. This is a correctness constraint, not a newly shipped optimization.

`requestVideoFrameCallback` fires when a video frame is sent to the compositor. It is broadly available since October 2024, provides `mediaTime`, `presentedFrames` and timing metadata, and may arrive a display refresh late. Its callback rate is capped by the lower of video rate and browser paint rate. Use it for revision/availability observations; do not make it the authoritative audio/beat clock or promise frame-exact deadlines. [MDN API and timing caveats](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback).

## A practical anticipatory-readiness experiment

The following is a proposed application design inferred from the upstream lifecycle constraints, not an upstream library feature or a confirmed missing implementation:

1. Derive a bounded upcoming-cut plan from the existing musical transport: destination source, source timestamp, target cut time and plan generation. For the requested eight-count experiment, begin preparation eight beats before the transition (480/BPM seconds under constant tempo), using the actual beat grid for variable tempo. Keep the visible/musical section switch at its existing boundary. Prioritize the nearest known cut; avoid warming every source at once.
2. Separate readiness stages: source metadata/bytes, target seek/decode completion, and a usable GPU frame. `preload="auto"` is a browser hint about downloading, not a guarantee that the future target frame is decoded or resident. `readyState` describes currently available media data, not ownership of a particular future cut frame. [Preload](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preload), [readyState](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/readyState).
3. Prepare an inactive source/standby decoder before its cut. Do not seek the currently visible element to a future target. Promote a prepared frame only when its source identity, target timestamp and plan generation match the current request; reject late completions from superseded plans.
4. Retain the current valid cut-cover while preparing its replacement. Cap standby decoder count, retained frame count, total texture bytes and work per tick; evict distant/invalidated entries. Derive the lookahead interval from measured preparation latency and memory pressure, rather than prescribing an untested fixed number of milliseconds.
5. Measure prepare-start, seek-complete, first matching frame, GPU-ready and cut-present times. Compare cut p95/p99, missed/black/stale frames, freeze duration, dropped frames, memory and active decoders under identical media/effects. Include seek, loop boundary, rapid plan changes, hidden/resumed tabs and source removal.

A resident bank exchanges preparation latency for resource use. As a lower-bound illustration, one tightly packed 1280×720 RGBA8 image is 3,686,400 bytes (3.52 MiB); two such images for eight decks are 56.25 MiB before allocation overhead, decoder surfaces, effects and feedback. This is arithmetic, not a measurement of browser VRAM. A small bank of near-future frames is a better initial experiment than unbounded decoded-video caching.

## Worker WebCodecs: useful architecture, separate scope

The WebCodecs Working Draft dated October 19, 2026 exposes `VideoDecoder` in dedicated workers and transferable `VideoFrame`s. `decodeQueueSize` counts pending input requests; it is not the number of usable decoded frames. Decoder outputs require their own bounded queue. `flush()` emits pending outputs and requires a key chunk for subsequent decoding, so calling it once per frame would disrupt ordinary sequential decoding. Close discarded/consumed frames and release decoder resources promptly. Codec and hardware support remain platform dependent; the standard requires no particular codec. [WebCodecs specification](https://www.w3.org/TR/2026/WD-webcodecs-20261019/).

Inference: demux/decode in a worker can reduce main-thread coordination work and give explicit frame scheduling, but does not remove hardware decoder limits, transfer costs or GPU residency pressure. Keep it as a separately benchmarked playback/export strategy with codec detection, backpressure, cancellation generations and a fallback. It is not a prerequisite for testing lookahead with the existing HTML-video architecture.

## What could make the recent optimizations worse

- **Immediates:** incorrect per-draw rewrites can leave stale beat/timeline values; fallback compilation failures or extra shader paths can hurt startup. The official API targets tiny, frequently changing data; large uniform structures still belong in buffers. Use the local differential tests and long live comparisons, not API novelty, to decide. [Chrome immediates announcement](https://developer.chrome.com/blog/new-in-webgpu-149-150).
- **Shared external/owned binding:** a common shader interface can reduce variants, but does not abolish external-texture lifetime, color conversion or format restrictions. Validate imported video and owned textures separately, including seek covers and feedback. Keep the actual binding probe and fallback. [Chrome texture-view binding announcement](https://developer.chrome.com/blog/new-in-webgpu-137).
- **Cache/replay:** fewer object updates can accidentally stop the video upload or a changing parameter. Babylon's merged fix above is a concrete warning about this class of failure; it is not evidence against all caching.
- **Preloading:** simultaneous seeks/decodes can compete with active playback. Admission limits and cancellation are part of the experiment, not cleanup to add afterward.
